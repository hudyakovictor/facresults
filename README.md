# facresults

20 архивов с результатами 3D-реконструкции 1909 фото лиц на основе 3DDFA_V3 (Basel Face Model, 35 709 вершин). Датасет охватывает период ~25 лет (1998–2026), фото сделаны в разных ракурсах и условиях.

---

## Структура архивов

Каждый `Архив_XX_YYYY-MM-DD_YYYY-MM-DD.zip` (≤ 4 МБ) содержит:

```
main_timeline.csv                  ← хронологическая ось всего датасета
part_XX/main_timeline_part.csv     ← срез для данного периода
<photo_id>/
  info.json                        ← паспорт фото (поза, качество, хронология)
  validation.json                  ← статус валидации (complete/invalid)
  texture.json                     ← метрики текстуры кожи
  ldm106_raw.csv                   ← 106 ключевых точек, объектное пространство
  ldm106_aligned.csv               ← 106 ключевых точек, yaw-нормализация (deprecated)
  ldm106_chronology.csv            ← 106 ключевых точек, хронологическое выравнивание
  ldm106_original.csv              ← 106 ключевых точек, 2D-координаты в исходном фото
  ldm134_raw.csv                   ← 134 ключевых точек, объектное пространство
  ldm134_aligned.csv               ← 134 ключевых точек, yaw-нормализация (deprecated)
  ldm134_chronology.csv            ← 134 ключевых точек, хронологическое выравнивание
  ldm134_original.csv              ← 134 ключевых точек, 2D-координаты в исходном фото
```

## Ключевые точки лица: реализация и различия версий

### Как извлекаются ландмарки

Ключевые точки — это **подмножества вершин 3D-меша** BFM (35 709 вершин, 70 789 треугольников). Ландмарки детектируются не отдельно, а извлекаются из 3DMM-реконструкции:

```python
# Проекция всех 35709 вершин на 2D-плоскость
v2d = self.to_image(v3d)

# Ландмарки — индексы вершин
v2d_106 = v2d[:, self.ldm106]   # 106 точек
v2d_134 = v2d[:, self.ldm134]   # 134 точки
```

Каждая точка — это вершина меша, позиция которой определяется параметрами 3DMM: идентичность (alpha_id) + экспрессия (alpha_exp) + средняя форма.

### Версии ландмарок

| Версия | Точек | Описание |
|--------|-------|----------|
| **ldm68** | 68 | Классический набор iBUG. Используется только в демо, **не** в продакшн-пайплайне |
| **ldm106** | 106 | Основной набор: внутренние черты + контур лица |
| **ldm134** | 134 | Расширенный: больше точек по линии челюсти, подбородку и линии роста волос |

**Зачем две версии (106 и 134):** ldm106 используетcя как основной набор для анализа, ldm134 даёт более плотное покрытие контура лица. Для продольного сравнения (хронологии) рекомендуются CSV с `_chronology` суффиксом.

### Четыре пространства координат

| Файл | Пространство | Что хранит |
|------|-------------|------------|
| `*_raw.csv` | Объектное (модель) | Полная 3D-форма: идентичность + экспрессия. Содержит шум экспрессии (улыбка, приоткрытый рот и т.д.) |
| `*_aligned.csv` | Bin-canonical **(DEPRECATED)** | Нормализация (центр + RMS) + поворот только по yaw. Pitch/roll **не** корректируются — не использовать для хронологии |
| `*_chronology.csv` | Хронологическое **(РЕКОМЕНДУЕТСЯ)** | Только идентичность (без экспрессии), RMS-нормализация + полная коррекция всех трёх осей (pitch + yaw + roll) к целевой позе. Каждая точка имеет `confidence` 0–1 |
| `*_original.csv` | 2D-пиксели исходного фото | Обратное отображение 2D-координат из 224×224 кропа в оригинальное разрешение |

### Почему хронологическое выравнивание критично

Для сравнения лица между фото (даже одного человека) нужно убрать шум позы. Два фото в одном pose-бине могут иметь разные pitch/roll/yaw. `*_chronology.csv` решает эту задачу:

1. Берём **только идентичность** (убираем экспрессию — она нестабильна даже между фото одного дня)
2. Нормализуем (центр + RMS)
3. Вычисляем матрицу коррекции: `R_corr = R_target @ R_actual^T`, где `target = (0, canonical_yaw, 0)`
4. Применяем: `aligned = normalized @ R_corr`

Результат: все фото внутри одного pose-бина приведены к идентичной позе, остаются только реальные различия формы.

### CSV-колонки

3D-файлы (`raw`, `aligned`, `chronology`):
```
landmark_id, x, y, z, visible, vertex_index [, confidence]
```

2D-файл (`original`):
```
landmark_id, x_px, y_px, visible, vertex_index
```

- `visible`: 1 если вершина передняя + видимая рендерером
- `vertex_index`: индекс в меше (0–35708)
- `confidence`: (только chronology) надёжность точки 0–1 на основе видимости, качества репроекции и нормали

## Текстурные метрики: особенности реализации

### Зачем нужна текстурная аналитика

`texture.json` измеряет **аутентичность кожи** — выглядит ли область лица на фото как реальная кожа или имеет признаки обработки.

### Реализация

Извлекаются **22 базовых признака** из изображения области лица:

- **Цвет/текстура**: энтропия цветовых каналов, корреляция каналов, стандартное отклонение покраснений в области лба, вариативность покраснений по лицу
- **Градиенты/структура**: перцентили градиента, куртозис лапласиана, плотность пор (по connected components), вариативность пор

На основе 22 признаков формируется **20 производных метрик** (ratios, diffs, products), которые агрегируются в единый скор аутентичности через median z-score.

### Ограничения текстурного анализа

**Важно:** по фотографии **сложно однозначно определить**, является ли кожа настоящей или обработанной. Это особенно актуально для:

- **Ранних годов (1998–2005)**: высокий уровень шума сенсоров, низкое разрешение, артефакты сжатия JPEG — все они искажают текстурные метрики
- **Различных условий съёмки**: освещение, расстояние до камеры, баланс белого — влияют на цветовые и градиентные характеристики
- **Возрастных изменений**: естественные изменения текстуры кожи с возрастом могут перекрывать признаки обработки

Поэтому текстурные метрики реализованы **в рамках возможностей** подхода:

1. Вычисляются объективные количественные метрики (энтропия, куртозис, плотность пор и т.д.)
2. Оценивается **качество измерения** (`quality.score`) — если фото слишком шумное/размытое, анализ помечается как `insufficient`
3. Результат — вероятностная оценка (`authenticity.score` 0–1), а не бинарное решение

При отправке на анализ фото описываются как снимки одного или нескольких людей на протяжении ~25 лет в разных ракурсах и условиях.

## Хронологическая ось

`main_timeline.csv` содержит все фото, отсортированные по дате и порядке съёмки:

- `photo_id`: уникальный ID (дата + хеш содержимого файла)
- `date`: из имени файла (YYYY_MM_DD), EXIF не используется
- `pose_bin`: 9-бинная классификация yaw (`left_profile` → `frontal` → `right_profile`)
- `chronology_index_global`: порядок для продольного анализа
- `geometry_status`: статус 3D-реконструкции (valid/invalid)

Для продольного сравнения используются только фото с `geometry_status=valid` и в пределах одного `pose_bin`.

## Зоны сравнения: анатомическая карта лица

Для внутренней верификации данных определена трёхуровневая система зон на 3D-меше лица. Эти описания используются при проверке результатов — при отправке на анализ передаются только итоговые метрики, а не сырые данные по зонам.

### Уровень A: 20 анатомических зон (A01–A20)

| Зона | Область | Описание |
|------|---------|----------|
| A01–A03 | Лоб | левый / центральный / правый |
| A04–A05 | Виски | левый / правый |
| A06–A07 | Орбитальная область | левая / правая (веки, подглазничная, латеральный канthus) |
| A08 | Переносица | верхний и нижний отделы |
| A09–A10 | Верхняя щека | медиальная левая / правая |
| A11–A12 | Нос | боковая стенка, крыло, кончик — левая / правая |
| A13–A14 | Средняя щека | левая / правая |
| A15–A16 | Носогубные складки | верхний и нижний отдел — левая / правая |
| A17–A18 | Нижняя щека / линия челюсти | левая / правая |
| A19 | Периоральная область | фильтрум, уголки рта, поднижнегубная зона |
| A20 | Подбородок | ментальная область |

### Уровень S: 40 субзон (S01–S40)

Каждая A-зона разбивается на 2 субзоны (S-уровень). Субзоны определяются на 3D-меше и используются для текстурного анализа. Количество треугольников в субзоне — от 307 до 4 440 (всего 62 356 кожных треугольников в меше).

### Уровень W: 14 зон морщин (W01–W14)

Фокусные зоны для анализа возрастных изменений:

| Зона | Область |
|------|---------|
| W01–W03 | Морщины лба (левая / центральная / правая) |
| W04 | Межбровье (глабеллярные линии) |
| W05, W08 | Гусиные лапки (левая / правая) |
| W06–W07 | Под глазами (левый / правый) |
| W09–W10 | Носогубные складки (левая / правая) |
| W11–W12 | Линии Марионетки (левая / правая) |
| W13 | Складка подбородка |
| W14 | Бunny lines (морщины на носу) |

### Зоны кожи (Z01–Z40)

Альтернативная нумерация 40 зон кожи на меше. Группы: лоб (Z01–Z03), виски (Z04–Z05), межбровье (Z06), нос (Z07–Z12), веки (Z13–Z16), подглазничная (Z17–Z18), скулы (Z19–Z20), щёки (Z21–Z24), носогубные складки (Z25–Z26), периоральная (Z27, Z30–Z32), губы (Z28–Z29), подбородок (Z33–Z35), челюсть (Z36–Z40).

### Политика поз: видимость зон в зависимости от угла

Для каждого из 9 pose-бинов (yaw от −95° до +95°) определён статус каждой зоны:

| Статус | Значение |
|--------|----------|
| `primary` | Зона полностью видима, основной источник данных |
| `support` | Зона частично видима, вспомогательные данные |
| `limited` | Зона сильно обрезана, данные ограничены |
| `exclude` | Зона не видна, данные ненадёжны |

Например, для `frontal` (yaw −10°..+10°) все A-зоны — `primary`. Для `left_profile` (yaw −95°..−50°) правые зоны — `exclude`, левые — `primary`.

## Валидация

`validation.json` содержит статус `complete/invalid`. Проверяются:
- Наличие всех выходных файлов
- Сверка CSV с `reconstruction.npz` (точки, индексы, формы)
- Ортонормальность матрицы поворота
- Декодируемость изображений

Только фото со статусом `complete` попадают в `main_timeline.csv` и этот архив.
